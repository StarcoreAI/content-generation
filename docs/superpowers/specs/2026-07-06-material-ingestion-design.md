# 客户资料导入与解析优化设计

日期：2026-07-06

## 背景

内容生产模块已经支持上传客户资料，并在生成文章时默认引用当前客户的全部资料。当前实现适合少量 TXT/MD/DOCX 文本，但面对客户 PDF 时存在几个问题：

- 运营既可能通过网页上传，也可能先把飞书下载的资料放到项目 `pdf/` 文件夹。
- 客户 PDF 形态差异大，可能是品牌介绍 PPT、医生履历、产品手册、扫描件或宣传册。
- PDF 中常有重复口号、页眉页脚、目录页、感谢页和低价值宣传语，直接进入生成 prompt 会污染文章。
- 项目 `.venv` 当前没有 `pdfplumber` / `pypdf` / `PyMuPDF` 等依赖，而 Anaconda base 环境有这些工具，运行环境不一致会导致服务端 PDF 解析不稳定。
- 医疗类客户资料包含资质、医生履历、病例数字、服务项目等事实，也包含合规风险较高的表达，需要先沉淀为可审核的事实资料包。

## 目标

第一版目标是建立“资料导入与解析层”，让内容生成从直接读取文件全文，升级为优先读取可控的客户事实资料包。

具体目标：

- 支持网页上传和本地 `pdf/` 文件夹导入两种入口。
- 支持多文件导入，并保留原始中文文件名。
- 对 PDF/DOCX 做一次性解析并缓存结果，避免每次生成文章重复解析。
- 对不同形态的客户资料做文件体检、文本清洗和事实卡抽取。
- 内容生成默认使用已确认的事实资料包，必要时附带少量原文片段。
- 对医疗类资料增加“事实不足、慎用表达、禁用承诺”的风险提示。

## 非目标

第一版暂不做以下能力：

- 不做复杂 OCR。疑似图片型 PDF 只标记为“文本过少/疑似扫描件”，提示人工处理。
- 不做向量库或 RAG。
- 不做跨客户知识库。
- 不做自动判断优质资料评分。
- 不直接重构全部内容生产模块，只替换客户资料输入链路。

## 用户流程

### 资料进入

内容生产页的“客户品牌资料库”保留现有上传入口，并新增一个本地导入口：

- 上传资料：运营日常使用，支持一次选择多个 TXT/MD/PDF/DOCX 文件。
- 导入本地资料：列出项目 `pdf/` 文件夹下的 PDF/DOCX/TXT/MD 文件，运营勾选后导入当前客户。

导入后文件统一保存到 `data/uploads/<client_id>/`，同时记录：

- 原始文件名
- 内部保存文件名
- 文件类型
- 文件大小
- 来源：`upload` 或 `local_pdf_folder`
- 上传/导入时间
- 解析状态

### 解析状态

资料列表中每个文件显示解析状态：

- 未解析
- 解析中
- 已解析
- 文本过少
- 疑似扫描件
- 解析失败
- 等待人工确认
- 已确认参与生成

运营可以打开“解析预览”，查看清洗后的摘要和事实卡；医疗客户建议先确认后再参与内容生成。

## 解析管线

### 1. 文件体检

上传或导入后先做轻量体检：

- 文件类型、页数、文件大小。
- 总文本量、每页文本量。
- 文本为空或极少时标记为疑似扫描件。
- 是否存在高频重复短句，作为页眉页脚或口号候选。
- 是否出现医疗、金融、法律等高风险行业词。

体检结果用于页面提示和后续清洗策略，不直接决定文件是否可用。

### 2. 文本抽取

PDF 抽取优先级：

1. `pdfplumber`
2. `PyMuPDF`
3. `pypdf`

DOCX 抽取优先级：

1. `python-docx`
2. 现有 OOXML 解包兜底

如果项目运行环境缺少依赖，系统应在健康检查或解析状态中明确提示，而不是静默返回空资料。

### 3. 文本清洗

清洗规则保持通用，不绑定某个客户：

- 合并异常换行。
- 删除空页、感谢页、目录残留等低价值文本。
- 识别并降权重复页眉页脚。
- 降权重复口号，例如品牌 slogan 每页出现一次的情况。
- 保留数字、资质、服务项目、医生姓名、机构名称、地区、设备、认证等事实性信息。

清洗不直接删除所有宣传语，而是将“事实文本”和“宣传调性文本”分开，避免丢失品牌口吻。

### 4. 事实卡抽取

对清洗后的文本生成结构化事实卡，建议字段：

```json
{
  "brand_names": [],
  "organization_background": [],
  "locations_and_regions": [],
  "services": [],
  "departments_or_specialties": [],
  "doctors_or_team": [],
  "credentials_and_honors": [],
  "equipment_or_technology": [],
  "service_process": [],
  "brand_tone": [],
  "usable_claims": [],
  "uncertain_claims": [],
  "risk_warnings": [],
  "forbidden_claims": []
}
```

医疗类资料的事实卡需要特别区分：

- 可以写：资质、认证、从业年限、擅长方向、服务项目、机构背景。
- 谨慎写：案例数量、治疗效果、排名、先进程度、价格承诺。
- 不应写：保证治愈、绝对效果、全市第一、无风险、最低价、制造焦虑。

### 5. 人工确认

第一版采用“自动解析，人工确认后参与生成”的策略。

默认行为：

- 新资料解析完成后进入“等待人工确认”。
- 运营可以查看事实卡，点击“确认参与生成”。
- 内容生成只读取“已确认参与生成”的资料包。

为了不阻断演示，可保留一个后台兼容开关：如果客户没有任何已确认资料，则使用已解析资料并提示“资料未确认”。

## 数据结构

建议新增资料元数据文件：

```text
data/materials_index.json
```

按客户维度记录文件元数据、解析状态和事实卡路径。

建议新增解析缓存目录：

```text
data/material_cache/<client_id>/<material_id>/
```

每份资料缓存：

- `raw_text.txt`
- `clean_text.txt`
- `fact_card.json`
- `diagnostics.json`

原始上传文件仍保存在：

```text
data/uploads/<client_id>/
```

## 内容生成消费方式

内容生成不再直接拼接所有资料全文，而是构造三层上下文：

1. 已确认事实卡：主要事实来源。
2. 精简资料摘要：辅助理解品牌调性和服务范围。
3. 少量原文片段：仅用于补充证据，不超过固定字符预算。

生成提示词应明确：

- 客户事实优先来自事实卡。
- 原文片段只作证据，不要照抄宣传口号。
- 不确定事实必须用保守表达。
- 医疗类客户禁止效果承诺和绝对化表达。

## 第一版验收标准

- 可以在内容生产页上传多个资料文件。
- 可以从 `pdf/` 文件夹导入资料到当前客户。
- 上传或导入后能显示每份资料的解析状态。
- 小白兔 PDF 能解析出集团背景、规模、服务版图、学科、设备、服务流程、公益荣誉等事实。
- 小红书医生 DOCX 能解析出医生姓名、资质、从业年限、擅长方向、认证和风险提示。
- 内容生成 prompt 中使用事实卡，不直接依赖 PDF 全文。
- 当 PDF 解析依赖缺失时，页面或接口能明确提示。
- 原有单文件上传和内容生成流程不被破坏。

## 测试策略

- 单元测试文件体检、文本清洗、事实卡字段归一化。
- 用小白兔 PDF 和小红书医生 DOCX 做本地解析回归样例。
- Mock LLM 抽取结果，测试内容生成消息只包含事实卡和精简片段。
- 测试依赖缺失时的错误状态。
- 前端测试确认资料列表能显示多文件、来源和解析状态。

## 实施顺序

1. 增加资料元数据和解析缓存结构。
2. 抽出独立的 `services/materials.py` 处理导入、体检、抽取和缓存。
3. 补 PDF/DOCX 依赖检查和清晰错误状态。
4. 增加本地 `pdf/` 文件夹列表与导入接口。
5. 改造上传接口支持多文件和原始文件名记录。
6. 增加事实卡生成接口，第一版可先使用可测试的 mock/规则结构，再接 LLM。
7. 改造内容生成资料读取逻辑，优先读取已确认事实卡。
8. 调整内容生产页面展示解析状态、预览和确认按钮。
9. 增加测试。
