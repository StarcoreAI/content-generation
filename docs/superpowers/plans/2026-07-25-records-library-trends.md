## 共同背景（为什么做）

爬取记录库现在是"扁平列表 + 筛选"，运营看不到长期变化。本次给同一份 `raw_records.json` 数据加三个只读聚合视图，全部放在**爬取记录库页**（`#page-records`），目标是给内容生产提供选题参考：

1. **按问题搜索 → 各平台提及变化序列**：看某个问题在各平台上品牌提及的"翻面"（之前提现在不提=预警，之前不提现在提=见效）。
2. **高频引用文章的新进/留存**：按当天日期展示引用池——新进（今天首次出现）、留存（标注已留存 N 天）。**不做"消失"**（用户拍板砍掉：当前发文走代发，我方文章无法可靠判断，消失预警价值不成立）。
3. **引用来源站份额按时间变化**：域名层比文章层稳定，看趋势该画在这层；回答"稿子该发到哪类站"。

用户已拍板的设计决策（不要重新讨论）：

- 品牌提及率长期曲线**不做**（汇报向指标，对内容生产无直接参考价值）。
- 发布登记表归因匹配/"我方发布"徽章**本次不做**（代发场景 URL 不可靠）。
- 文章层不画单篇趋势曲线（高换血率下没法看），只做"当天新进/留存"快照。
- 竞品实体份额、引用池换血率、引用位置分析均不在本次范围。

硬约束提醒：只读聚合、不写任何数据文件；不动当日整理页、爬虫链路、本地 worker；沿用现有多租户隔离（越权 404）；单 gunicorn worker 约束不变；不引入图表库等新前端依赖（用表格/CSS 条形展示）；PowerShell 用 `;` 不用 `&&`；开发只跑单测，不做真实爬取。

数据基础（探索确认过，直接用）：

- 主数据 `data/raw_records.json`，经 `load_client_records`（`services/records.py`）过滤，单条记录含 `question`、`group_id`、`source_platform`、`refs[]`（`{position,title,url,platform}`，其中 `platform` 是引用来源站名）、`brand_mentioned`、`crawl_time`、`today`、`client_id`。
- 文章归一化键复用现有 `canonical_article_key(title, url)`（`services/record_insights.py` 有现成用法）。
- 当前全库约 200 条 / 2MB，请求时全量内存聚合即可，**不要做预计算缓存**。

## 任务块一：问题提及变化 + 高频文章新进/留存

### 改动点

新建 `services/record_trends.py` 放聚合函数；`app.py` 加只读路由；前端在爬取记录库页加两个分区。

#### 1. 按问题搜索 → 各平台提及变化序列

- 聚合函数：输入某客户全部记录 + 问题文本，输出按平台分组的时间序列：`{platform: [{date, mentioned, records}]}`，按日期升序。
- 口径：同日同平台多条记录（多轮）合并为一格，**任一条提及即记提及**；`records` 为该格的记录条数，供前端悬浮提示。
- 路由：如 `GET /api/records/question_trend?client_id=&question=`，问题文本精确匹配（前端问题下拉已有现成问题列表，复用）。
- 前端：记录库页新增"问题提及变化"分区——选择问题后，每平台一行，按日期渲染 ✓/✗ 序列（带日期），一眼看出翻面位置。无记录的平台不显示。

#### 2. 高频引用文章 新进/留存（按当天）

- 聚合函数：输入某客户全部记录 + 锚定日期（默认最近一个有记录的日期），输出：
  - `new_entries`：该日引用池中**首次出现**（全历史首次被引日期 == 锚定日）的文章，按该日被引次数降序，取前 20；
  - `retained`：首次出现日期 < 锚定日且该日仍在池中的文章，标注 `retained_days`（锚定日 − 首次被引日期，自然日）和累计被引次数、涉及平台，按留存天数降序，取前 20。
- 文章键用 `canonical_article_key`；每篇输出 `title`、`url`、当日被引次数、累计被引次数、首次被引日期、涉及的 AI 平台列表。
- 路由：如 `GET /api/records/article_pool?client_id=&date=`，date 可省略（默认最近有记录日）。
- 前端：记录库页新增"引用文章池"分区——日期选择器 + 新进/留存两个列表；留存条目显示"已留存 N 天"。

#### 3. 通用要求

- 路由必须走现有客户访问校验（`require_client_access` 或同等），越权 404。
- 聚合纯函数放 `services/record_trends.py`，方便单测；路由只做参数解析和权限。

### 验收标准

- 单测全绿。
- 真实验收由用户执行：选记录最多的客户，打开记录库页——
  1. 选一个问题，各平台提及序列与原始记录人工抽查一致（翻面位置正确）；
  2. 文章池视图：某留存文章的"首次被引日期/留存天数"与筛选原始记录核对一致；新进文章确实是当天首次出现；
  3. 用另一运营账号访问该客户的新接口返回 404。

### 测试要求

- fixture 构造多日期、多平台、多轮记录，覆盖：同日多轮任一提及即提及；新进/留存判定（含首次日期计算）；文章键归一化（同 URL 不同标题合并）；日期缺省取最近有记录日；空数据返回空结构不报错。
- 越权 404 测试对齐现有隔离测试写法。
- 前端 wiring 静态断言对齐 `tests/test_content_generation_ui.py` 现有模式。
- 跑相关模块后跑 `.\run_tests.bat` 全量；完成后独立提交，更新 `接手文档.md` 记录库能力描述。

## 任务块二：引用来源站份额按时间变化

> 依赖任务块一验收通过后开工。

### 改动点

#### 1. 域名聚合

- 从 `refs[].url` 提取注册域名（无 scheme/带 www 等做归一化；url 为空或无效时回退用 `refs[].platform` 站名作为聚合键）。
- 提取逻辑写成独立纯函数并单测（中文站名回退、末尾斜杠、http/https、www 前缀、无效 URL）。

#### 2. 份额时间序列

- 时间粒度：按**周**聚合（ISO 周）；每周每域名份额 = 该域名被引次数 / 该周总被引次数。
- 输出最近 12 周、按累计被引次数排前 10 的域名的份额序列，其余合并为"其他"。
- 路由：如 `GET /api/records/source_trend?client_id=`。

#### 3. 前端

- 记录库页新增"引用来源站变化"分区：每域名一行，按周渲染份额（CSS 条形或百分比表格，不引图表库），能看出"某站份额在涨/在掉/稳定"。

### 验收标准

- 单测全绿。
- 真实验收由用户执行：对记录最多的客户，抽一周人工数一个域名的被引次数核对份额；确认周序正确、"其他"桶存在；越权 404。

### 测试要求

- 覆盖：域名归一化各边界；周切分正确；份额合计为 1（或空周处理）；top10+其他合并；空数据不报错。
- 跑相关模块后跑 `.\run_tests.bat` 全量；独立提交，更新 `接手文档.md`。
