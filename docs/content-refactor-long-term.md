# 内容链路 · 长期规划文档

更新时间：2026-07-19

这份文档记录短期重构（见 `docs/content-refactor-short-term.md`）之后的方向：分发、观测归因、平台微调、记忆与自进化。它写的是想法和目标，不是施工规格；实施前需要再细化，且大部分依赖短期重构落地和归因数据积累。

## 1. 总体叙事

整个系统的长期形态是**一个会从结果里学习的内容 agent**，闭环是：

```text
生成 -> 发布 -> 被 AI 引用(每日爬取已在采集) -> 归因 -> 更新记忆与策略 -> 下一批内容更强
```

我们的独特优势：反馈回路的采集端**已经存在**——问题组每天在向各 AI 平台提问，答案里的引用链接每天在入库。缺的只是"我们的文章在哪"（发布登记）和"两头对上"（归因匹配）。

## 2. 依赖链与顺序

```text
发布登记表 -> 归因匹配 -> { 平台偏好矩阵 | 模块权重自进化 | 反思任务 }
```

**发布登记表是唯一建议提前到短期做的长期项**：两张表一个录入页的工作量，但历史发布记录不可事后补——晚三个月做，就永远缺三个月的归因样本。字段：文章 id（关联生成记录与溯源）、发布平台/站点、URL、标题、发布日期、是否带广告标注。

## 3. 分发

第一步不是自动发布，是登记（见上）。之后的策略空间：

- 一稿多发管理：同一篇铺几个站、错峰发布（竞品已在这么玩，我们的引用情报第 0 步归并已在采集这个情报）。
- 渠道价值评估：归因数据回来后，可统计"哪个站的文章更容易被哪个平台引用"，反哺投放渠道选择。
- 自动化发布放最后：涉及各站点对接，收益不如登记+归因高，不着急。

## 4. 观测归因

- 核心任务：爬取记录中的引用 URL/域名 与 发布登记表匹配（精确 URL 优先，域名+标题相似度兜底），产出每篇文章的"被引用成绩单"：哪个平台、回答了哪个问题、首次/最近被引时间、存活时长、对应回答是否提及品牌。
- 第一版产出是**给运营看的报表**，不自动下结论。这与 content-plan 中"记录库按问题和引用文章重组"的方向是同一件事的两面，实施时合并考虑。
- 成绩单同时按溯源字段聚合：每个骨架/开头模块/竞品组合/FAQ 问题的引用率——这是后面一切自动化的数据基础。

## 5. 平台微调

归因数据积累后（预计需要几十篇有结果的文章），"平台偏好"从猜测变成查表：

- 每个骨架/模块 × 每个 AI 平台的引用率矩阵。
- 抽样器增加"目标平台"条件维度，按矩阵加权抽样。
- 发布平台同理（新闻站/知乎/官网知识页各吃哪种文体）。
- 已有的初步信号（样本极小，仅作假设）：豆包引用过激进排名体，DeepSeek 引用的是中性观察体。不要在没有数据前把这个假设写死进规则。

## 6. 记忆架构与自进化

### 6.1 记忆分层（短期重构已埋好字段）

- 两层存储：短期（任务级：简报、批内指纹、修改链上下文）+ 长期（四个持久库：写法库、客户知识库、竞品库、经验库）。
- 三层作用域：`global` / `industry` / `client`，读取时合并。新行业冷启动 = 行业层为空 + 全局层立即可用，系统结构不变。
- 有效期字段：政策事实类条目过期自动降级并进缺口报告。
- 生命周期：候选 -> 生效 -> 停用，全库统一状态机。

### 6.2 客户知识库

客户知识库放在长期建设，不进入短期施工。短期仍使用 `latest_injection.md` / `latest_web_supplement.md` 作为资料包，并由运营在内容生产页显式选择使用或不使用；后续由内容生产一阶段的信息整理 LLM 按单篇任务决定本次要覆盖什么、哪些角度可展开；明显矛盾、夸大、无依据的内容由质量门禁兜底。

启动条件不是“有资料就建库”，而是以下信号出现后再做：

1. 同一客户反复生成内容，资料包变长且重复信息明显；
2. 质量门禁反复拦截同类事实问题、口径冲突或无依据表述；
3. 运营多次把同一类表达改成固定口径；
4. 多篇文章需要稳定复用客户定位、服务边界、禁用承诺、补料缺口。

第一版客户知识库只做结构化长期记忆，不做复杂 RAG。条目建议包含：客户基础信息、可稳定使用的定位/服务/优势表述、限制使用或必须带前提的话术、已发现冲突点、长期补料缺口、运营批准过的表达偏好。每条必须带来源、状态、作用域、更新时间，机器整理出的内容先进入候选，只有运营确认或多次门禁/修改链证据支持后才生效。

出货方式也要克制：客户知识库不直接喂给写作 LLM 当“真相大全”，而是作为简报 LLM / 信息整理 LLM 的输入，用来约束本篇内容覆盖、禁用项和保守表述。最终文章仍由质量门禁检查明显矛盾、无来源主张和不当承诺。

### 6.3 运营经验库

第四个长期库，进货渠道按成本从低到高：

1. AI 修改指令（短期重构的 `modify_instruction` 列已在积累，免费）；
2. 运营终稿 diff 的 LLM 摘要（"运营把 X 改成了 Y——疑似话术偏好"）；
3. 弃用文章的简报组合（负样本）；
4. 显式录入入口（一个文本框，最低摩擦）。

条目 = 情境标签（行业/子类型/平台/模块）+ 经验 + 证据计数 + 作用域 + 状态。机器提炼的进"候选"，证据攒够或运营点头才"生效"。出货：软的按标签匹配注入简报 LLM；硬的（反复出现）升级成门禁规则。

### 6.4 自进化 = 多臂老虎机 + 反思任务

- **老虎机**：抽样器对骨架/模块的选择是拉杆，归因的"被引用与否"是奖励，用 Thompson 采样或 ε-greedy 更新抽取权重。短期重构里的"10-15% 自由发挥槽位"就是探索项；效果好的新写法沉淀回库 = 策略空间自动扩张。
- **反思任务**：周期性（如每周）LLM 对比高引用与零引用文章，输出假设，自动生成写法库/检查清单/经验库的候选条目，运营一键批准。带人类监督的 self-improvement。
- 门禁拦截记录（短期已留痕）作为负样本一并进入反思输入。

### 6.5 检索策略升级阈值

现在：标签过滤 + LLM 全量判断（库几十到几百条时足够）。升级触发条件：某库条目数大到 LLM 一次装不下且标签筛不准——预计最先撞线的是经验库（修改指令积累快）和客户知识库判重。届时改"标签粗筛 + 向量召回 + LLM 重排"。代码上把"取相关条目"抽成独立函数，换实现时上层无感。不上图数据库：溯源查询只有一跳，关系表即图。

## 7. 引用情报流水线提速

现状：stage0 定性、stage1 解剖、stage2 入库比对都是逐条串行 LLM 调用，一轮合计约 30-40 次，加上抓取的浏览器兜底，整轮耗时明显。已记录的优化方向（按性价比排序，等运营实际等待成为痛点再做）：

1. **小并发并行调用**：LLM 调用是 IO 密集型，stage0 和 stage1 的逐篇调用可以用小线程池并行（沿用抓取 `fetch_workers` 的模式，遵守单 gunicorn worker + 多线程约束）。注意 stage2 必须保持串行——同轮内后面的卡要能命中前面的卡刚建的候选条目。
2. **跨轮增量扩展**：已解剖 URL 台账已实现；可扩展到 stage0 定性结果缓存（同 URL / 同归并组的判定跨轮复用），稳态下每轮只处理新出现的文章。
3. **模型分工**：stage0 定性是轻量判断，可换更快更便宜的模型；解剖和入库比对保留强模型。
4. **抓取侧观察**：高引用文章反复 fetch_failed（如 eol 站点）造成的信息缺口比速度问题更大，浏览器兜底的重试策略和耗时值得单独审视。

## 7b. Phase 2b 降级项回补清单（2026-07-20 记）

Phase 2b（内容生产改造+质量门禁）为控制范围做了三处降级，落地条件成熟后回补，避免遗漏：

1. **竞品实体库（短期 Step 1）**：Phase 2b 期间抽样器竞品子集槽位直通、不抽样，简报和门禁只用竞品 Markdown。竞品实体库（短期文档 4.3 结构：结构化字段+来源类型+强主张清单+安全描述+置顶/拉黑）落地后回补：抽样器按置顶/拉黑抽 3-5 家竞品子集；质量门禁代码层加机构名白名单和竞品强主张复读匹配（本期这两项在 LLM 层做）。
2. **质量门禁代码层机构名白名单**：依赖竞品实体库+客户品牌的结构化实体名，随第 1 项一起回补。
3. **版本修改链（Step 4）与一键批量生成（Step 6）**：本期 SQLite 已一次性加好 `parent_id`/`root_id`/`batch_id` 列（留空），做这两步时无需再改表结构，直接补链查询/批次执行逻辑即可。

## 8. 明确不做 / 暂缓

- 无人值守自动发布、多平台发布对接：暂缓到归因跑通后评估。
- 自动改写提示词（无人审核的 prompt 自进化）：不做，进化只发生在"库条目权重"和"运营批准的新条目"两个受控层面。
- 多模型自动评分替代人工审核：不做。
- 复杂 RAG / 图数据库 / 独立记忆服务：不做，理由见短期文档决策记录第 9 条。
